## User-specified requirements

- Provide a `config.toml` flag to enable model routing for delegated subagent tasks.
- Before dispatching a delegated task, the main/default model decides whether a simpler configured model is sufficient.
- Route the task to either the normal/default model or the configured simpler model based on that decision.
- When the simpler model handles a task, it should finish its response and then assess whether the normal model could give a materially better response because the simpler model did not answer adequately.
- If the simpler model recommends escalation, wait for a response from the normal model before treating the task as complete.
- The user has now requested two routing features: (1) route all messages and subagents; and (2) route only when the main thread asks a subagent to perform a task.
- Use `gpt-6.1-sol` as the regular model and `gpt-6-luna` as the simple model.
- For updater integration with upstream main, merge upstream into the feature branch rather than rebasing the feature commits. (Confirmed 2026-11-06.)
- If a main-thread message is routed to the simpler model, the response remains in the main thread.
- If a simpler-model main-thread response recommends escalation, continue with the regular model in that same main thread.
- If a simpler-model subagent recommends escalation, launch another subagent using the normal/default model.
- For `model_routing = "all"`, treat the initial main-thread request as a routing-only preflight: do not answer the user's task in that request. If the model completes without selecting a tier, discard that preflight text and safely continue with the regular model and its normal tools. (Clarification, 2026-11-05: user observed the model answering the task instead of routing.)
- Enable `[agents].model_routing = "all"` in the user's Codex config.
- Add usage tracking so users can see tokens routed to the simple model and the simple model's percentage, including local models and use without ChatGPT sign-in.
- Show simple-model input and output token counts as separate counters. Do not present only a combined input-plus-output total; separate counts must remain available so users can calculate costs.
- Display the model used for each assistant message in the UI, potentially next to elapsed-time/model metadata.
- Render the model name to the right of the completion timestamp, not on top of or overlapping the timestamp (clarification, 2026-11-01).
- Add a per-message history note recording the model/tier used, so future routing decisions can reason about earlier model choices and outcomes.
- Update routing instructions to review prior model-tier notes and response success/failure before selecting a tier for the current response.
- Show both configured routing models (`gpt-6-luna` and `gpt-6.1-sol`) in the `/models` picker. (User request, 2026-11-01)
- After building, testing, and verifying, remove generated build outputs that need not coexist with the installed release; keep daily source-updater builds low in disk usage. (User clarification, 2026-11-01)
- Configure the daily source updater to build this adaptive-routing feature branch. (User request, 2026-11-02)

## Agent-proposed implementation choices (not user requirements)

- Keep the clean OpenAI `origin/main` checkout intact and have the daily updater build from a dedicated linked worktree tracking the user's public feature fork/branch. Only clean committed remote state is eligible; dirty source-tree edits are never silently included. Record remote and branch in install receipts.
- Use a local-only rebase of the fetched feature tip onto `origin/main`; abort conflicts, restore the clean worktree, and leave the installed binary unchanged. This avoids rewriting public branch history while producing an up-to-date build input.
- Benchmark routing latency with `subagents_only` as the main-thread-routing-off baseline and `all` as the feature case, holding prompt/model/effort constant and preserving ephemeral per-run event logs.

- Keep routing opt-in so existing model selection remains unchanged unless enabled.
- Represent the two requested scopes with `[agents].model_routing = "all"` or `"subagents_only"`; use `[agents].simple_model` for the simple-tier model and default the regular tier to the current/default model.
- In `all` scope, make the initial main-thread model call a bounded routing-tool decision, then switch subsequent sampling within the same main thread. The simpler main-thread model can request same-thread continuation with the regular model.
- Require the routing tool on the initial classification request so the model cannot skip the model-selection step and answer directly.
- In either enabled scope, guide the main model to select the simple model on child spawn; a simple child reports an escalation marker, and the main model retries the task in a new regular-model subagent.
- Use a bounded machine-readable escalation marker in the simpler agent's final response; the parent model should continue with the normal model when the marker requests escalation.
- Prefer one escalation attempt and preserve existing explicit model/role choices unless the routing tier was explicitly selected.

## Additional agent-proposed implementation choices (not user requirements)

- Show simple-tier input and output token counts separately, with corresponding input-share and output-share percentages against all reported model usage; do not use a combined-only token total or percentage.
- Prefer exact usage reported by providers; if local providers omit it, show a tokenizer-based estimate with an explicit estimate label or report unavailable rather than implying exactness.
- Persist compact per-response model/tier annotations in the rollout and expose bounded annotations in later model context.
- Keep per-message model labels in the transcript and usage totals in the thread/footer summary; avoid showing monetary cost where no reliable provider price applies.
